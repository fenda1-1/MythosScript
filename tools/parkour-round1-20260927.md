- 前后都开启 `parkourDebugLog`，关闭渲染调试。总时间从请求启动序列到首次观察其终点传送区域，并另外要求执行日志 `finished=true`、`outcome=success`。沼泽55的终点是链式下一段入口，不是大厅。

## 本批组合改动

1. `flowLandingCandidates` 在已有状态转换缓存未命中时才创建输入对象并计算朝向，减少重复 `atan2` 与分配。
2. `directRoute` / `flowLandingCandidates` 把固定起点的搜索高度边界移出模拟内循环。
3. `searchFlow` 每个候选只算一次累计帧数、出口距离和速度评分，排序复用已有 `Frame.score`。
4. `searchWithRunup` / `replaySupported` 在一次调用内复用已有碰撞索引，避免对子搜索或逐帧重复扫描完整碰撞列表。
5. 输入缓存关闭时跳过历史缓存键的坐标字符串拼接。

候选顺序、束宽、计算预算、碰撞/支撑/稳定落地检查保持原有规则；收益按组合报告，不声称某一小项独占收益。

## 归因方法

逐 tick 三轴位置变化小于 0.003 格、连续采样间隔不超过 150ms，且持续至少 0.2 秒，计为静止区间；包含没有执行器的等待。这是位置统计，不等同于纯搜索 CPU 时间，也包含必需的稳定/机关等待。超过 150ms 的日志缺口不硬算为静止。

各中继阶段用第一次观察到相应 `!goto` action 至下个中继/终点计时；因此包含中间等待动作，边界有采样误差。movement 类型耗时按相邻 tick 的当前动作归属，表示该动作占用的墙钟，不是纯行走用时。计划路径以 `planned_route` 事件为证，实际执行路径以 `analysis.json` 的 `route` 为证；失败与恢复保留在事件中。

### 沼泽55路线与阶段

原序列本来就只有一次 goto（5.5,46,-3054.5）。阶段 71.203 → 61.828 秒，planned_route 10 → 7，显式 fail 3 → 2，trajectory_plan 92 → 86。主要执行同一竖向关卡，包含中层折返和上层藤梯；节省不能归因于删中继。

- 中层 `(3,33,-3061) → (3,34,-3064)` 两次均搜索失败，落在 x约3.99/y33/z约-3060.04 静止 8.048 → 7.846 秒，随后记录空轨迹与 rejected_edge，并绕回32层再上行。这条坏边几乎没改善。
- 后测回退后的 x4.068/y33 再等待3.800秒；x4.499/y32 等待4.165 → 3.250秒。下层和中层的小等待、规划/重规划次数共同下降，并非某一处消失了9秒。
- 上层 `(9,43,-3054) → (8,44,-3055)` 仍反复一帧轨迹，静止6.709 → 6.301秒；两次最后都由 `This movement has taken too long (112 ticks, expected 11.005972741470003, movement MovementParkour). Cancelling.` 解围，再从45层重新选路到终点。
- 已找到后者的判定不一致：模拟到达用 `floor(y)==44`，执行器的 `playerFeet()` 使用 `floor(y+0.1251)`；实测 y=44.906651，模拟认44层、执行认45层，直到超时。本批未修该逻辑，作为下一批明确缺陷。
